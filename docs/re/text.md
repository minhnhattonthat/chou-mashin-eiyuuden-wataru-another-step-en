# Text engine, encoding, pointers

Disc: SLPS-01368 (Banpresto / Aspect, 1998-04-23). EXE `SLPS_013.68`: PS-X EXE, t_addr 0x80018000, file offset = addr - 0x80018000 + 0x800.

## Encoding (verified)

- Text is a stream of **16-bit little-endian codes**. No Shift-JIS anywhere (`tools/sjisscan.py`: only noise).
  - verified: `relsearch.py --width 2` on a RAM dump found わたくし / いらしたのね at 0x800DB5E8 (gojuon, あ=0x0001), and the
    same bytes sit in `FPRG/R00.BIN` at 0xD5E8. Decoded lines match the screen (work/qa/r3 f6000-f9000).
- **0x0001-0x01A3: common font** `FM16/MSG_CG.BIN`, glyph index = code + 0xA6 (16x16, 4bpp, 128 bytes/glyph, low nibble
  first, colours 1-F = antialias + drop shadow). Table: `tbl/jp_common.tbl`, generated by `tools/mktbl.py`.
  - 0x01-0x54 hiragana (gojuon, small kana and dakuten forms in their own rows), 0x56-0x8D katakana, 0x91-0xA9 katakana
    dakuten, 0xAA ？ 0xAB ！ 0xAC ー 0xAD ・, 0xB0-0xB2 水雷火, 0xB4-0xBD ０-９, 0xBE-0xC3 equipment icons, 0xC4-0xCF
    ○×△□／ ＋－×％：, 0xD0 ．, 0xD1-0xE5 Ａ-Ｕ (J/K are kanji cells 毒/化 at 0xDA/0xDB), then ~210 kanji up to 0x1A2.
  - verified kanji: 一 0x10E, 忍 0x176, 部 0x18D (decoded 「忍部一族」 matches screen).
  - Kanji 0xE6-0x1A2 read by eye into `tbl/kanji_rows.txt` (CG lines, read by mktbl.py). 0x3B and 0xC9/0xCA unread cells.
- **0x01A4+: per-room kanji**, allocated in order of first appearance in that room's script. Glyph = room font file index
  code - 0x1A4. verified: R00 族=0x1C3 = `M16_R00.BIN` glyph 0x1F, 申=0x1C4 = glyph 0x20.
  - Room fonts: `FM16/M16_Rxx.BIN` (xx hex: R0A = room 10, R0E = room 14), same 128-byte glyph format; up to 190 glyphs
    (max code 0x261). Episode-to-font map (verified): "Fonts other than MSG_CG / M16" below.
  - The same code means different kanji in different rooms: the table is per room (common + room).
- Text controls inside a message: 0x1000 newline, 0x2000 end of page/message. Menus and tables end strings with 0xFFFF
  or 0x9999 (ST.BIN choice lists: `[9999][0000][0000][0000]はい`).

## Room scripts (FPRG/R00-R14.BIN), verified

- Each `FPRG/Rnn.BIN` is a MIPS overlay loaded at **0x800CE000** (R00: RAM image == file, `work/qa/d1/ram.bin`), code
  first, then message banks, then data (event tables with absolute pointers into the overlay).
- Message record (event bytecode level, read by the interpreter around 0x80031F60-0x800329A0, script pointer
  0x8009C998): `FFFF 0000 0001 [A] 0100 0302 [B] <text> 2000`; one of A/B is 0x7FFF, the other an id word whose low byte
  is the message number in the bank (high nibble: portrait/window? **guess**). Values 0x0000, 0xFFFB-0xFFFE are
  interpreter controls (`80031FE0..8003209C`).
- **Bank pointers:** per room, a switch at 0x800321A0 (room id halfword 0x8009C90C, < 15, jump table 0x8001DEF8) loads
  `idx = u16 table[conv]`, then `start = u32 banks[idx]` into 0x8009C9A4. R00: banks at RAM 0x800DC5D8 (file 0xE5D8: 3
  pointers 0xCCD4, 0xD990, 0xE23C), idx table at 0x800DC5E4. The tables' addresses are hardcoded in the EXE per room
  (lui/addiu pairs in each switch case). The engine then walks the bank for the message id: **no per-message pointers**,
  and no 32-bit pointer word lies inside a bank (scan of R00). So banks can be relocated by rewriting only the bank
  pointer words, and English may change lengths freely inside a bank.
- Text ranges (`tools/msgscan.py`, message-like runs): R00 0xCCF4-0x12328 ... R14 0x1BCA0-0x285C6; ~9,600 runs total.
- **Second text area = NPC talk, per-message u32 pointers** (verified static, R00): after the event data, records of
  8 zero halfwords then `speaker：/text`, pages end 0x2000, a message ends **0x3000**. Reached through u32 pointer
  arrays at the overlay's tail: R00 0x1233C (16 ptrs -> 0x116AC-0x122C0) and 0x1237C (21 ptrs -> 0x109EC-0x1162C),
  then 0x123D0+ pointers to those pointer slots. Every room has the same layout: its last pointer array points into
  the end of its text range (R10 0x119EC[50], R14 0x25320[65]...; `re.py`-style u32 scan, 2026-11-13). So these
  messages relocate by rewriting one u32 each. The 48-entry arrays in the middle of each room are event tables.
  Reader: branch 0x800326DC (guess, not traced).
- Other branch tables (0x800DED28 etc.) in the switch read data that is text in R00: those cases are for other rooms.

### Page grammar and kanji readings (verified static, 2026-11-14; `tools/rooms.py`, `tests/test_extract.py`)

- `tools/rooms.py` finds 4,601 pages in R00-R14 (docstring has the full grammar): a page = text words (0x0000 = blank
  cell, 0x1000 newline, inline `B000 n`) ended by 0xN000 (N 2-F, not B; `4000 n`, `8000 n`, `C000 a b`, `F000 n` take
  args). Headers: `FFFF .. 7FFF`, `7FFF 01xx face voice`, `FFFF 0000 <id>`, `<cmd args> FFFF [0000]`, chained after a
  page, NPC u32 pointer targets (some aim at the 16 zero bytes before), and blocks the overlay code builds by
  lui/addiu (R08 0x163C0, R13 0x16780, R14 0x1BCA0). Every page roundtrips and decodes with no code past its font;
  every msgscan run is covered except 44 data runs in `tbl/room_data.txt` (actor tables, checked by eye).
- R13.BIN font split (`rooms.font`): M16_R12 for 0x1DAB0-0x212D7 and 0x22D78+, M16_R13 elsewhere.
- Kanji: all 201 common + 2,295 room glyphs read by eye from zoomed sheets into `tbl/kanji_rows.txt` (template
  matching against MS Gothic / Yu Gothic got 46% on known kana: useless). 73 readings marked `?`; `python -X utf8
  tools/jtext.py` lists them, `jtext.py sheet OUT.png R00:1F8 ..` renders any set big. Fonts hold real duplicate
  glyphs (R02 先 0x1AB/0x242, R07 社, R11 福, R12 行/誰/問); the codec writes the second as `[0242:先]`.
- 0xE8 in MSG_CG looks like Ｘ; 0x181 is the ▼ prompt glyph.
- Readings settled from context (2026-11-14, `jtext.py ctx`): the 16px font draws 女 like 廿/甘, 嬢 like 爆, 簡 and
  聞 (CG 0x131) like 闇. R13 0x16780-0x172EA is episode-12 text (M16_R12).
- **EXE text is narrower than the 0x6AA10-0x7CA9A span above** (verified static 2026-11-14): dialogue in room page
  grammar at 0x6AA10-0x6ACA8 (save lady), 0x77A80-0x77B88 (shop, もんペット), 0x79EC0 (inn), 0x7A4DC-0x7CAB4 (210
  item/system messages, table 0x7CAB8); menu strings ending 0x0000 at 0x77B8A-0x77CC8. The u32 arrays 0x70B6C,
  0x76884, 0x76B38, 0x76DBC aim at event records (0x6F364-0x7090C, 0x7532C-0x76764), not text.

### EXE text (static, 2026-11-13; offsets are file offsets, RAM = file + 0x80017800)

- Messages: lui/addiu pairs reach 196 of 668 runs; 410 sit in a referenced block. u32 pointer arrays (all verified as
  arrays of string starts by listing): 0x6A4D8 (59), 0x70B6C (224), 0x76884 (109), 0x76B38 (97), 0x76DBC (38),
  0x7808C (16), 0x78AD8 (16), 0x7CAB8 (210 -> 0x7A554+, the big system-message table), 0x7CF28 (19 key-item names),
  0x7D3B4 (19 key-item descriptions, 0x40 each), 0x7D7B0 (4 -> consumable-name sub-tables), 0x7DC5C (4 -> item-effect
  text sub-tables), plus small ones (0x77B8C, 0x79BF0, 0x79E44, 0x7A3F8, 0x7A548). Pointer arrays mean free lengths.
- **Fixed-width name fields** (no per-string pointer; code indexes base + i*stride; guess until a read is logged):
  key items 0x7CE18+ 0x10 (8 codes), consumables 0x7D400+ 0x10, item effects 0x7D7C0+ 0x14, **equipment
  0x7DC7C-0x7E1BC 0x10**, abilities 0x7F858-0x7F9A8 0x0E (7 codes), **mashin attacks 0x80094-0x801AC 0x14**,
  **enemy names 0x80300-0x80544 0x14** (lui/addiu builds 0x802EC = base - 0x14: 1-based index). A full 8-code name
  has no terminator (プロテクトバンド fills 16 bytes). English must fit these widths, or the tables move and the base
  references (lui/addiu, maybe also `$gp` = 0x8009C618) get rewritten: an engine decision for phase 5.
- Noise, not text: 0x67D94-0x69DD8 and 0x6A7B8-0x6A938 (0x80-stride numeric tables), 0x7F048-0x7F408 (0x40 records).
  Full list of table ranges that decode as text, per source: `tbl/menu_data.txt` (extract drops them, the coverage
  test waives them).
- More fixed fields (verified 2026-11-14 by layout): **key-item descriptions** 0x7CF74-0x7D3B4, 2 lines x 16 cells per
  item (u32 table 0x7D3B4 -> each pair, stride 0x40); **shop lines** 0x77BA0-0x77C20 (16 cells: `よろしいですか` +
  `はい　いいえ` share one line, おかねがたりません！！, ...); **monpet prompts** 0x77C58-0x77CC8 (16 cells, the last 8).
  Descriptions use codes >= 0x1A4 (`[01AF]`, `[0221]`, `[0226]`): menus borrow the loaded room font, so the reading
  depends on the episode (like `[0224]メダル`, 金 in R08/R09).

### Menu-source structure (phase 4, 2026-11-14; tools/extract.py, tests/test_extract.py test_menu_*)

- Strings can sit back to back with no terminator, so a string starts at every pointer target, and blank cells right
  after a target are kept as text (ST 0x104 `　バトルをつづける`: the cursor indent). BALLBAT cuts at u32 targets only
  (a code ref aims mid-string at 0x252E8).
- BALLBAT 0x2150C-0x226F4: names and battle messages reached by `[u32 cells, u32 ptr]` records (blocks 0x21530..,
  0x21A7C.., 0x22384.., 0x22708.., the bfont list 0x22AB4): **the game draws the record's cell count**, not up to a
  terminator (phase 5, 2026-11-14: a spilled 22-cell ふいうち！ drew its 5 JP cells; the lose message stops at its
  record's 14 of 16). `extract.CELL_RECORDS` puts the u32's offset in `len_at`, insert rewrites it. Block
  0x21E1C-0x21E94 is `[u32 id, u32 ptr]` (attack names, ids 3-6). Records decode as one kana and are dropped. Message
  fragments (`は`, `の`, `を手に入れた！`) are glued to names at run time. No other source has such records (swept).
- **BALLBAT battle-font item names** 0x22830-0x22A84: list `[u32 cells, u32 ptr]` at 0x22AB4 (40 items, ptr 0 ends),
  drawn by 0x800E1C30 with an 8x16 4bpp font at RAM 0x80110000 (glyph = code * 64 bytes, padded to 11 cells): code =
  common code + 0x0E for kana, 1-10 digits (`jtext.battle_table`, read from a battle RAM dump). Copies of the EXE item
  names: keep them in step. The font's file is not traced yet (phase 5, to add Latin glyphs).
- FDS: place names 0x120D8-0x124AC are 10-cell fields (`fds_places.json`; u32 table 0x124AC = first slot per
  episode), voice names 0x18550 7-cell fields (`fds_voices.json`, also in TTL), monpet name-entry kana grid 0x18468
  (data: phase 5 swaps in Latin letters).
- MACHINE 0x1761C/0x17630/0x17648 (`天翔登龍剣幻影招龍破`, `昇龍烈火爆裂聖剣斬る突く`, `リトライゲームをやめる`): no
  terminators, one code ref each: probably glyph sets the mashin battle uploads; waived as data until phase 5 finds how
  they are drawn.
- Codes >= 0x1A4 in EXE runs come almost only from those noise tables; menu text uses MSG_CG codes (guess: check the
  status screen in phase 2).

### Battle enemy names (found by the phase-5 marker tour, 2026-11-14)

- `YM/BR_02/ENE01-18.BIN`: battle enemy overlays loaded at 0x80104800 (file table). Names (2-4 per file, `ene/ENExx.json`)
  are reached by records `[u32 cells<<8 | idx, u32 ptr, u32 ptr name, u32, u32 ptr]`: the cell count is explicit and
  names sit back to back unterminated (ENE13 ラムネコップ|シェイクコップ). `extract.ene_names`. Phase-1 "YM: no text"
  missed them (short names, preceded by pointer words). A sweep of every other file for 4+ kana runs found only
  image data and sequential tables.
- Record word 2 (`ptr8`) = the **battle header name** (top right): bytes in the 8x16 battle font, NUL-terminated,
  char[12] slots (ENE06 0x25D4: 8), `kind: bname`; 0xEB = ・ (`[00EB:・]`, 0xBB is ・ too). BALLBAT 0x800D0B50 copies
  the record to 0x800F1C00 (cells), 0x800F1C04 (16-bit name), 0x800F529C (ptr8); 0x800DF310 draws ptr8 for
  `cells` letters, then blanks to 11: patched to stop at the NUL (insert.CODE).

### Fonts other than MSG_CG / M16

- **The 8x16 battle font is MSG_CG.BIN itself**, bytes 0-0x3B00 (code * 64, 236 cells: digits, kana, A-Z; render with
  `fontview.py --w 8 --h 16`). insert.py draws Latin over its kana from code 0x0F (BF_FIRST).

- `OUT/CNF_MSG.BIN` (98,688 B = 771 glyphs, 16x16 4bpp, verified by render): config-screen font, kana at the same cells
  as MSG_CG (あ = glyph 0xA6 + 0x01), more kanji after. TTL.BIN (config) strings index it (guess: check in config tour).
- **Room font per episode index (verified 2026-11-13, docs/re/debug.md):** switch at 0x800272F8 on 0x8009C90C, and
  RAM 0x80122500 == the font file in the warp states. Index 0-1 M16_R00, 2-3 M16_R02, 4-5 M16_R04, 6 R06, 7 R07, 8 R08,
  9 R09, 10 R0A, 11 R11, 12 M16_R12, 13 M16_R13, 14 M16_R0E. Overlays: index 0-11 = R00-R11.BIN, 12 and 13 = R13.BIN,
  14 = R14.BIN. So R01/R03/R05 use the R00/R02/R04 fonts, and R13.BIN text is drawn with M16_R12 in episode 12 and
  M16_R13 in episode 13: the table is per episode index (split R13.BIN's banks by episode in phase 4). M16_R14 (225
  glyphs) is not loaded by this switch (its first 8 KB equal M16_R0E: guess, the ending). The file table
  0x80077240 (`tools/filetab.py`) holds every font name with its load address.
- Earlier glyph-count guesses (R13 = M16_R13 for all of R13.BIN, R14 = M16_R0E) were partly right; the per-index map
  above replaces them.

Not 16-bit text (all runs decode to noise, `msgscan.py --menu` + decode, 2026-11-13): MOVIE, SBTTL, MEMORY, FD_STS,
FVHH/STAFF.BIN (credits: graphics or another format), FP*, FR*, FK*, IQ/*.CHG, YM/* (incl. MR_09/MBPRG code overlays),
license_data.dat. `FM16/R15_MES.BIN` is an image (prologue scroll, graphics.md G10), not text. Episode title cards are
glyph-composed from OUT/SUBTTL.CHG (graphics.md G6): their strings are atlas indices, not this encoding.
