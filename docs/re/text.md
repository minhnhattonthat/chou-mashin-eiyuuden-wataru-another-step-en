# Text engine, encoding, pointers

Disc: SLPS-01368 (Banpresto / Aspect, 1998-04-23). EXE `SLPS_013.68`: PS-X EXE, t_addr 0x80018000, file offset = addr - 0x80018000 + 0x800.

## Encoding (verified)

- Text is a stream of **16-bit little-endian codes**. No Shift-JIS anywhere (`tools/sjisscan.py`: only noise).
  - verified: `relsearch.py --width 2` on a RAM dump found わたくし / いらしたのね at 0x800DB5E8 (gojuon, あ=0x0001), and the
    same bytes sit in `FPRG/R00.BIN` at 0xD5E8. Decoded lines match the screen (work/qa/r3 f6000-f9000).
- **0x0001-0x01A3: common font** `FM16/MSG_CG.BIN`, glyph index = code + 0xA6 (16x16, 4bpp, 128 bytes/glyph, low nibble
  first, colours 1-F = antialias + drop shadow). Table: `tbl/jp_common.tbl`, generated by `tools/mktbl.py`.
  - 0x01-0x54 hiragana (gojuon, small kana and dakuten forms in their own rows), 0x56-0x8D katakana, 0x91-0xA9 katakana
    dakuten, 0xAA ？ 0xAB ！ 0xAC ー 0xAD ・, 0xB0-0xB2 水雷火, 0xB4-0xBD ０-９, 0xBE-0xC3 equipment icons, 0xC4-0xCF
    ○×△□／ ＋－×％：, 0xD0 ．, 0xD1-0xE5 Ａ-Ｕ (J/K are kanji cells 毒/化 at 0xDA/0xDB), then ~210 kanji up to 0x1A2.
  - verified kanji: 一 0x10E, 忍 0x176, 部 0x18D (decoded 「忍部一族」 matches screen).
  - Kanji 0xDA-0x1A2 still need OCR (`tbl/kanji_common.txt`, read by mktbl.py). 0x3B and 0xC9/0xCA unread cells.
- **0x01A4+: per-room kanji**, allocated in order of first appearance in that room's script. Glyph = room font file index
  code - 0x1A4. verified: R00 族=0x1C3 = `M16_R00.BIN` glyph 0x1F, 申=0x1C4 = glyph 0x20.
  - Room fonts: `FM16/M16_Rxx.BIN` (xx hex: R0A = room 10, R0E = room 14), same 128-byte glyph format; up to 190 glyphs
    (max code 0x261). Rooms 01, 03, 05, 11, 13 have no M16 file by that name (fonts elsewhere; M16_R11-R14 may be rooms
    17-20 or those). **guess**, verify which font is resident per room with a RAM probe in phase 2/4.
  - The same code means different kanji in different rooms: the table is per room (common + room).
- Text controls inside a message: 0x1000 newline, 0x2000 end of page/message. Menus and tables end strings with 0xFFFF
  or 0x9999 (ST.BIN choice lists: `[9999][0000][0000][0000]はい`).

## Room scripts (FPRG/R00-R14.BIN), verified

- Each `FPRG/Rnn.BIN` is a MIPS overlay loaded at **0x800CE000** (R00: RAM image == file, `work/qa/d1/ram.bin`), code
  first, then message banks, then data (event tables with absolute pointers into the overlay).
- Message record (event bytecode level, read by the interpreter around 0x80031F60-0x800329A0, script pointer
  0x8009C998): `FFFF 0000 0001 [A] 0100 0302 [B] <text> 2000`; one of A/B is 0x7FFF, the other an id word whose low byte
  is the message number in the bank (high nibble: portrait/window? **guess**). Values 0x0000, 0xFFFB-0xFFFE are
  interpreter controls (`80031FE0..8003209C`).
- **Bank pointers:** per room, a switch at 0x800321A0 (room id halfword 0x8009C90C, < 15, jump table 0x8001DEF8) loads
  `idx = u16 table[conv]`, then `start = u32 banks[idx]` into 0x8009C9A4. R00: banks at RAM 0x800DC5D8 (file 0xE5D8: 3
  pointers 0xCCD4, 0xD990, 0xE23C), idx table at 0x800DC5E4. The tables' addresses are hardcoded in the EXE per room
  (lui/addiu pairs in each switch case). The engine then walks the bank for the message id: **no per-message pointers**,
  and no 32-bit pointer word lies inside a bank (scan of R00). So banks can be relocated by rewriting only the bank
  pointer words, and English may change lengths freely inside a bank.
- Text ranges (`tools/msgscan.py`, message-like runs): R00 0xCCF4-0x12328 ... R14 0x1BCA0-0x285C6; ~9,600 runs total.
  The upper ends include a second text area per room (e.g. R00 0x10D28+) not covered by the 3 banks: find its reader
  (other branch at 0x800326DC uses tables at 0x800ECD9C/0x800ECDB0).
- Other branch tables (0x800DED28 etc.) in the switch read data that is text in R00: those cases are for other rooms.
